这本魔导书的每一页都印着横线，行距锁死一格。于是任何一个偷偷长高的行盒，都会让它**后面所有**的文字一起漂出格线——罪证离现场最远。

## 行盒是并集，不是一个数

行盒高度 = 块内所有 inline box（含 strut）按基线对齐后的**并集**；而单个 inline box 的半行距 = `(line-height − 字身) / 2`。

推论有点反直觉：**任何 `font-size` 小于父级的行内元素**（`code`、`kbd`、小号上标），字身更小 → 半行距反而更大 → 它的下边缘探出中文 strut 的下边缘，行盒被撑高。

实测里，正文块高度出现 61 / 92 / 122 / 183px（2.03 / 3.07 / 4.07 / 6.10 格），一篇之内从 +1 一路漂到 −13。

## 第一条：行内代码要压 line-height

```css
.art-page code{ line-height:1; }
.art-page pre code{ line-height:inherit; }
```

取 1（等于自身字号）时，code 的上下缘缩进 strut 之内，行盒改由 strut 决定，精确落回周期，**视觉零变化**——背景色块画的是字身，不受 line-height 影响。

代码块必须豁免：`pre` 的正文整个包在 `<code>` 里且跨多行，那里的 code 就是行的生产者，一豁免每行只剩 .92em。

**判据只与字体的 (ascent − descent) / em 比例有关，与 font-size 无关**——所以把 code 字号调回 1em 治不好（实测仍撑 0.8px），只能压 line-height。上界依赖字体度量、算不准，**不要套公式，用测量工具实测**：好工具会直接告诉你哪一行、哪个字符在撑高。

## 第二条：两个引擎，两种撑法

同一条机制，在两个引擎上露出不同的脸：Chromium 下等宽字体的字身比例恰好不撑（实测 90 / 150 / 60 精确），Firefox 下撑（实测 91.5 / 152.5 / 61，即每行 30.5）。

所以「Chrome 精确 30px」从来不是一条定律，只是它没踩到你踩的那个点。把 `pre code` 的字号一并拉平之后，半行距与 strut 一致，与字体度量彻底无关——这才是根治，不是调参。

## 第三条：滚动条也算半格

`pre` 内容超宽时，Chromium 会在块底长出一条 **15px** 的横向滚动条，块高凭空多半格（75 = 60 + 15），其后的正文全部掉出格线。不超宽的 `pre` 恰好 90 / 150 整格。

一眼辨别的办法是看**盒差**（`offsetHeight − clientHeight`）：非零即说明块高里有边框或滚动条在占位。修法是让滚动条不占布局高度，横向照样能滚：

```css
.art-page pre{ scrollbar-width:none; }
.art-page pre::-webkit-scrollbar{ height:0; }
```

两条都要写：一条给 Firefox，一条给 Chromium 与 Safari。

> 稿纸的横线是一条契约：行盒里任何一个偷偷长高的字符，都会让整页为它让路。
