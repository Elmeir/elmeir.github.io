把列表的 marker 从行盒里摘出去之后，它就只剩观感问题了。然而一个纯粹用来「好看」的圆点，照样让我翻了四次车。

## 起因：marker 参与行盒计算

Firefox 让原生 `::marker` 参与行盒高度计算。无序列表的 bullet `•`（U+2022）在 Windows 上不在正文用的中文字体里，回退到字身更大的符号字体 → 半行距随之变大 → 下缘探出 strut，`li` 的行盒被撑高 2px，其后的块跟着累积漂移（一篇里能漂到 +6）。

铁证是一对对照：有序列表的 `li` 精确 30px。两个 `li` 的 `font-size` 与 `line-height` 完全相同，唯一的差别是 marker 字符不同（`•` 与 `1.`），结果相差 2px。

**调字号没用**——判据是两个 em 比值相减，与 font-size 无关，marker 字号调小反而更撑。要让 marker 不进换行盒，只能自绘 + 绝对定位：

```css
.art-page ul, .art-page ol{ list-style:none; }
.art-page li{ position:relative; }
.art-page ul > li::before{
  content:"·";
  position:absolute; left:-14px; top:0;
}
```

绝对定位元素不参与行盒计算，这是唯一能彻底免疫的写法。由此也得到一条通用结论：**任何依赖原生 `::marker` 的列表，在要求行盒精确的场景下都不可靠**；`list-style-position: inside` 更糟，它让 marker 变成 inline，直接进换行盒。

## 第一次：`•` 是「小圆点」字形，放大不显大

`font-size` 从 `1em` 一路加到 `1.8em`，反馈仍是「还是很小」。因为 `•` 的字身占比本就小，等比放大只是把小点放成大一点的小点。

要「显大」得**换字符**：`●`（U+25CF 黑圆）在同字号下的视觉直径明显更大。

## 第二次：改字号必然改间距

点是绝对定位的，`left` 是相对 li 内容盒的负值。点一变大，圆点与正文左缘的间隙跟着变，不改就会贴字或离得太远。

而且 **`padding-left` 必须 ≥ |left|**，否则点会凸出容器左缘，与上方的标题对不齐。

## 第三次：`top: 0` 只在点很小时看不出问题

要垂直居中就用 `top: 50%; transform: translateY(-50%)`。点放大之后，`top: 0` 的偏移肉眼可见。

## 第四次：覆盖 marker 位置必须提权

`.art-page ul > li::before` 的特异性是 (0,1,3)，而局部的 `.contact-list > li::before` 只有 (0,1,2)——**写了不生效**。覆盖时必须补一层容器类。

行盒全程不受影响（绝对定位的字号、字符、left、top 都不参与行盒计算），但**换字符之后仍要重测一次**：「不参与布局」不等于「不用验证」。

## 附带：内容容器有两个

自绘 bullet 的规则原本只挂在文章页那个容器上，而章节页的每个面用的是另一个容器。于是作者页的列表既拿不到 bullet（点直接消失），又继承了另一个容器的相对行高——**相对值继承的是那个数字本身，不是 px**，后代一改字号就按自己的 font-size 重算：13px × 1.85 = 24.05px，脱格且逐行累积漂移。

修法是两个容器都挂，不写特例。而排查手法属于最值钱的那一类：选择器看着对、样式却不生效时，用宽窄两个选择器各跑一次测量——**总数 29、命中 23，多出来的 6 个就是不在那个容器里的那批**。数量差就是结构证据，比翻 DOM 快一个数量级。

顺带两条推论：

- **行高周期只能写死，不能靠继承**。祖先给一个数字行高，任何后代改字号都会按自己的字号重算一遍。
- **改标签会反转规则的「生 / 死」**。一个单类选择器的 `font-size: 13px` 压不过「容器 + 标签」规则里的 15px——那 13px **从未生效过**，实际一直渲染 15px。把 `p` 换成 `li` 之后写成同分的选择器（靠写在后面胜出）才真正生效，字号当场从 15 掉到 13，用户立刻察觉「字变小了」。所以把 `p` 改成 `li`（或反之）时，先查一遍「容器 + 标签」规则里有哪些属性会跟着换掉——**`p → li` 影响的往往不止字号**。

> 圆点不参与布局，却参与了所有人的判断：太小、太挤、太淡——先问是不是该换个字符，别只在数值上做算术。
